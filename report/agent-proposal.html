Abstract

We present the S.O.U.L. Agency, a ticket-driven multi-agent workflow system. Work enters as tickets — created manually, or filed automatically by intake clerks that triage Gmail and WhatsApp. A code-driven dispatcher (not a chatting model) moves each ticket through a verified pipeline: Scout researches and writes a structured plan with checkable acceptance criteria; Builder writes real files into a sandboxed workspace using native function calling; Sentinel runs deterministic checks plus a criteria-bound verdict and either closes the ticket or routes specific fix notes back (max two rebuilds). A Watchdog runs a MAPE-K self-healing loop over the machine and the queue: it scores PC pressure and throttles parallel tickets (2 / 1 / 0), flags stuck tickets, and reports service health. Per-ticket model-call budgets cap token burn. The design is deliberately centralized: agents never free-chat — a direct response to recent failure taxonomies showing 41–87% task-failure rates in open-ended multi-agent frameworks. The full system runs on a student laptop at zero cost and is demonstrated live on a Kanban board.

1. Introduction and Motivation

A chatbot answers from its weights; when it does not know, it guesses. An agent (Russell & Norvig) perceives an environment and acts on it to achieve goals. A multi-agent workflow goes further: specialized agents divide labor — intake, planning, building, review — coordinated through shared, inspectable state. Industry interest is large and measurable (agent markets estimated near USD 7–8B in 2025 with steep forecast growth; orchestration frameworks report tens of millions of monthly installs with named enterprise deployments), and every major AI lab shipped an agent SDK during 2025–2026.

Our motivation is a working version of a software agency on one laptop: requests arrive from the two channels a student actually lives in (email, WhatsApp), become tickets, get built by a crew, get reviewed, and close — while a watchdog keeps the machine alive. Academically, the system demonstrates PEAS, all classical agent types, environments, planning, verification, and self-healing in one build.

3. Problem Statement

Student work arrives fragmented across email and chat, gets built (if at all) in one unreviewed pass, and dies on overloaded laptops with no record. The problem is to build a rational multi-agent system that (i) converts inbox/chat noise into tracked tickets, (ii) plans, builds, and reviews each ticket with verification gates, (iii) protects the host machine via load-adaptive scheduling, and (iv) keeps every decision inspectable — all on student hardware at zero recurring cost.

4. Objectives

  1. Ticket store with a dispatcher-enforced lifecycle: OPEN → PLANNED → BUILDING → REVIEWING → DONE (or FAILED with reasons kept).
  2. Intake clerks that triage Gmail/WhatsApp into tickets with dedupe and caps.
  3. Scout (structured plan + acceptance criteria), Builder (sandboxed file writes via native function calling), Sentinel (deterministic checks + criteria-bound verdict).
  4. Watchdog MAPE-K loop: pressure score, adaptive parallelism (2/1/0), stuck-ticket flags, service health.
  5. Per-ticket model-call budgets; send-gates on all outward actions; Kanban board UI.
  6. Evaluation: fresh build tickets + ablations + honest failure log.

5.3 Safety box

Builder writes are confined to workspace/ in code (absolute paths and ../ rejected); no shell execution, no sends, no deletes — worst case is an ugly file in a sandbox. Outward sends anywhere stop for human approval. Secrets are never baked into images (.dockerignore + runtime env).

7. The Multi-Agent Position — Centralized and Verified

Multi-agent systems are booming (fastest-growing agent-market segment; tens of millions of framework installs; an agent SDK from every major lab) — but booming ≠ better by default. A NeurIPS 2025 failure taxonomy measured 41–87% task-failure rates across open multi-agent frameworks; controlled studies show the multi-agent edge shrinking 10%→3% as base models improve at 4–220× token cost, debate sycophancy near 85%, and single-agent wins once baselines pass ~45%. Our position: centralized dispatcher, structured artifacts, verified handoffs, no free agent dialogue — the configuration the literature identifies as containing error amplification (~4× vs ~17× unverified). The agency's own comparison runs (single vs pipeline) test this claim directly.

10. Evaluation Plan

  1. Build tasks (fresh tickets): small utilities + one-pagers of graded difficulty; each with Scout-written acceptance criteria.
  2. Metrics per ticket: outcome (DONE/FAILED), model calls, wall time, rebuild rounds, load before/after.
  3. Ablations: criteria-bound vs free-judgment Sentinel; native vs text-protocol Builder; single pass vs review pipeline.
  4. Artefacts: ticket histories as transcripts; one full Thought→Action→Observation trace; failure log with fixes.
  5. Guardrail tests: send-permission probes (must pause), path-escape writes (must refuse), secret-planted code (must flag).

11. Build Log — Failures That Improved the Design

  1. Parser rejected its own roles (Scout/Sentinel JSON "unparseable") → accept any dict, validate keys per role.
  2. Sentinel judged without evidence → RCI-style grounding: file contents fed to the judge.
  3. Hygiene checker vs the todo app (flagged "TODO" inside a todo app) → placeholders count only in code comments.
  4. Text-protocol writes break on file payloads (unescaped quotes killed JSON 3×) → native function calling for Builder: payloads as typed args. Prompt-protocol for chat, native tools for builders — an architecture finding.
  5. Shell killed by its own pkill pattern (ops lesson) → PID-file process management; never match your own command text.
